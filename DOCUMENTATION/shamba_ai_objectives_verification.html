OBJECTIVE I

Design a system architecture for image processing and crop disease detection.

✓ MET

Evidence in the document

  • Section 2.1 argues for a three-tier architecture (presentation / application logic / data) and reviews client-side vs. server-side image processing trade-offs for low-resource users.
  • Section 4.2 ("System Architecture") states the implemented system followed exactly this three-tier split, naming FastAPI's static file middleware, the FastAPI REST layer, and SQLite in WAL mode as the three tiers.
  • Figure 4.1 is captioned as the system architecture diagram showing frontend → FastAPI backend → smart pipeline (ONNX/Gemini) → SQLite.

Evidence in the codebase

  • backend/app.py mounts the frontend via StaticFiles and wires five routers (auth, detect, admin, history, chat) — the application logic tier.
  • backend/db/database.py opens SQLite with PRAGMA journal_mode=WAL and foreign_keys=ON, matching the data-tier design described in the text.
  • backend/ai/predict.py implements the image-processing pipeline referenced in the objective: pre-processing (image_utils.py) → Gemini Vision call → ONNX fallback → advice lookup.

OBJECTIVE II

Implement a web-based crop disease detection system using AI-powered image analysis.

✓ MET

Evidence in the document

  • Chapter Four describes iterative (Agile) implementation of the front end, back end, database, and AI module, and states all three objectives were achieved using the Gemini Vision API.
  • Section 4.6 documents the FastAPI + SQLite back end, and 4.6.2–4.6.3 give the actual table schemas and testing levels used.

Evidence in the codebase

  • POST /api/detect (routes/detect.py) is a real, working endpoint: it validates the upload, runs predict_disease(), looks up advice, stores the record, and returns disease name, confidence, severity, symptoms, treatment steps, products and prevention — a genuinely web-based, end-to-end system rather than a mock-up.
  • gemini_vision.py sends the image plus a structured pathologist-style prompt to gemini-3.1-flash-lite and parses a strict JSON response — this is the "AI-powered image analysis" the objective calls for, not a hard-coded label list.
  • A genuine offline fallback exists: model.py runs a local ONNX MobileNetV2 session when Gemini is unavailable or low-confidence, so the system degrades gracefully rather than failing outright.
  • Supporting features beyond the bare objective are also implemented: JWT auth (auth_utils.py), scan history (history.py), an admin dashboard (admin.py), and a post-diagnosis chat endpoint (chat.py).
OBJECTIVE III

Evaluate the performance and usability of the crop disease detection system.

✓ PARTIALLY MET

Evidence in the document

  • Section 4.6.3 reports unit, integration, and end-to-end testing, and states the Gemini Vision API was tested on 25 sample images across five crops against expert-identified ground truth.
  • Appendix C gives concrete numbers: 100% correct identification across the 25 test images, an average confidence of 80.2%, with potato/tomato scoring highest (83.6% / 83.0%) and kale/onion lowest (76.8% / 77.8%).
  • Section 4.5 discusses usability-oriented design decisions — a minimal-step scan flow and a mobile-first, vertically-stacking layout aimed at farmers with limited tech experience.

Evidence in the codebase

  • The confidence-threshold logic in predict.py (accept Gemini only above 20%, ONNX only above 40%) is itself a built-in performance gate, consistent with the accuracy figures reported in Appendix C.
  • GET /api/health in app.py exposes live status of the ONNX model, the Gemini key, and the database — a small but real operational-performance check.
Gap: Section 2.3 of the literature review sets up the System Usability Scale (SUS) as the intended usability instrument, but this draft does not yet contain a corresponding results section with actual SUS scores or participant/user-testing numbers — the quantitative evidence currently on hand is technical accuracy/confidence testing (Appendix C), not a formal usability study. If a usability survey was run, its results should be added as a proper section (e.g. Chapter Five) before final submission; if it wasn't, that's the one piece of Objective III still to close out.
